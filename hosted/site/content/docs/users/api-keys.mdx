---
title: API keys
description: What the CLI, an agent and docker login authenticate with. Self-service, shown once, revocable at any time — including the last one.
---

An API key is a bearer token carried as `Authorization: Bearer <key>`,
and it is what every non-browser client uses: the CLI, an MCP client,
`docker login` at the instance's registry (username plus the key as the
password), a CI job calling the API.

## Making one

On **Account → API keys**, or:

```bash
cubeship user api-key create laptop
cubeship user api-key list
cubeship user api-key revoke 3
cubeship user api-key rotate          # replaces the key this CLI is using
```

A key is shown **once**. Only its hash is stored, so nothing can hand it
back; a key that was lost is revoked and replaced. Keys are named
(`laptop`, `ci`, `mcp`) so the list says what each is for, and an
account may hold any number.

The first account gets no key at setup: keys are self-service, and one
nobody is shown would be a live credential lying around for nothing.

## Revoking is never refused

Including the last one. A key that has leaked has to be able to go
*now*, and being made to mint a replacement first would keep the
leaked one live for as long as that took. What replaces the refusal is
knowing: the account screen says what revoking this one costs — the CLI
until you make another, or, for an account with no password, the way
in — and asks.

## Rotating

`rotate` revokes the key the CLI is signed in with and issues a new one
in its place, saving it locally. `docker login` sessions using the old
key stop working.

## What a key may do

A key never does more than its owner may, and it can do less. Two
things decide it, both chosen when the key is made:

| Access | What it does |
| --- | --- |
| `read` | Lists, logs and status. Never a variable, a credential, a download, or a change. |
| `deploy` | What a member does — create, configure and deploy apps — whatever the owner's role. |
| `full` | Everything the owner may. The default. |

**Projects.** A key can be held to a list of projects. The others are
not there — they answer as not found — and neither is what belongs to
the whole instance: databases, object stores, servers, templates,
settings. It can still list its projects and their apps, create apps in
them, and push and pull their images.

```bash
cubeship user api-key create claude --access read
cubeship user api-key create ci --access deploy --project shop
```

**The limit is in the key, not in the prompt.** Over MCP a key is not
offered a tool it does not allow — an agent cannot be talked into
calling what it was never shown — and the API refuses the same requests
at the door. A deleted project leaves a key held to it reaching nothing,
never everything.

A restricted key cannot make one that reaches more than it does, cannot
revoke keys and cannot change the password. Rotating keeps the scope.
What every key did is in the [audit log](/docs/users/audit).

## The role travels with the key

A key does what its owner may do, within its access. Blocking the owner
refuses every key at the door; deleting the owner deletes them.
