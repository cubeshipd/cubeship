## Added

**Template updates.** An installation's page now compares the template it was installed with against the one the catalog lists now, and shows **Update** beside **Uninstall** when they differ. The comparison is of the templates themselves, not the catalog's commit, so a template republished unchanged is not offered as an update. A change only to a source-built template's Dockerfile is not detected.

**Preview before applying.** **Update** first lists everything it would create, change, remove or leave in place, and asks only the questions the installation has no answer for; a secret it generated before is read back from the app that holds it. The update then runs in the background and redeploys the apps it created or changed. Secrets it generates are shown once, as at install.

**Domains can move between apps.** A domain the template no longer gives an app is removed before new domains are added, so a template that moves a domain to another app updates cleanly. Nothing else is deleted: databases, stores, volumes, apps and variables the template no longer declares are left as they are.

**API and MCP.** `GET /api/template-installs/{id}/update` previews an update and `POST /api/template-installs/{id}/update` starts it; the second answers 409 when the installation already matches its template. Agents use `preview_template_update` and `update_template_install`. Updating needs the admin role.

## Upgrade notes

No database migration is needed. If an update fails at any step, what it created is deleted, the apps it changed are set back and redeployed — removed domains included — and the installation keeps its template. Existing installations recorded their template at install, so they can be compared right away; for example, a Jian installation from before 1.0.0 is offered the update that moves its domain to the new web app.
