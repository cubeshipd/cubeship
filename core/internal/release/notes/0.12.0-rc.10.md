## Fixed

**Git provider connections.** Cubeship checks that its registered GitHub App still exists before offering its installation link. A deleted App can be registered again from Git Providers; replacing an App clears installation records that belong to the old one. Bitbucket now connects with a scoped API token instead of asking operators to configure an OAuth consumer. Existing OAuth connections remain available.

**Private Bitbucket builds and pushes.** Dockerfile and Railpack builds use the Bitbucket credential when cloning a private repository. Push webhooks match the provider as well as the repository name, so a same-named GitHub app cannot be deployed by a Bitbucket push. Bitbucket repository discovery uses the current workspace and repository APIs.

**Cubeship registry image details.** Image tags in the built-in registry now report their size and build date where the registry provides that metadata. Tags remain visible if metadata cannot be read.

## Changed

**Build source.** Repository choices from connected GitHub and Bitbucket accounts appear in one searchable list, with their provider identified. Source and Repository share the first row; Branch and Build method share the second.

**DNS and firewall.** DNS zones can be filtered by record type, record types can be searched when adding a record, and CNAME records offer one value. The Firewall page uses a simpler server-rule layout and asks for a hold action before turning protection off.

**Dashboard consistency.** DNS, Firewall, Git Providers, and Registries use the same page spacing and section headers. Registry selection controls and searchable selects follow the current dashboard pattern.

**Project upkeep.** CI checks were scoped and cache paths corrected; contribution and security guidance and pull-request size labels were refreshed.

## Upgrade notes

Select 0.12.0-rc.10 from an instance with prereleases enabled, or name this version when installing. Migration 00069 preserves existing Bitbucket OAuth connections and adds API-token connections. New Bitbucket tokens need user, workspace, and repository read scopes. Deploy on push still requires a Bitbucket repository webhook and a matching signing secret. This candidate does not move the stable latest release or image tags.
